# max-ai-bridge

AI-бот для MAX на PyMax: пересылает сообщения нейросети и отвечает в том же чате.

## Что нового в этой версии

- Версии библиотек в `requirements.txt` зафиксированы (`==`), чтобы обновление
  зависимостей не ломало бота исподтишка.
- Несколько провайдеров/агрегаторов нейросетей одновременно (OpenRouter, Groq,
  Google AI Studio и т.п.) и переключение модели/провайдера прямо из чата
  командами, без правки `.env` и перезапуска.
- Настройки (провайдер, модель, системный промпт, поиск) хранятся отдельно
  **для каждого чата**.
- Вопросы и ответы сохраняются в SQLite (`cache/history.db`) и подмешиваются
  в следующий запрос как контекст диалога (сколько последних пар — настраивается).
- Веб-поиск для нейросети через **SearXNG** (свой инстанс) или **Keenable**
  (публичный поисковый API для AI-агентов, работает без ключа) — можно включить
  на постоянной основе для чата или дёрнуть разово командой.
- Системный промпт задаётся отдельно для каждого чата.

## Запуск

`AI_PROVIDERS` в `.env` — необязателен. Минимум для старта — только `MAX_PHONE`:

```bash
python -m venv venv
source venv/bin/activate       # Windows: venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env
$EDITOR .env                   # достаточно заполнить MAX_PHONE

python main.py
```

При первом запуске PyMax попросит SMS-код в консоли — введите его.
Сессия сохранится в `cache/main.db`, повторно код спрашиваться не будет.

Провайдеров нейросетей на этом этапе ещё нет — их можно задать сразу в `.env`
(см. "Провайдеры и агрегаторы" ниже), либо добавить прямо из чата после
запуска — см. следующий раздел.

## Как пользоваться

В любом чате/группе, где состоит этот MAX-аккаунт, напишите:

```
@a расскажи анекдот про питона
```

Бот ответит в том же чате. Префикс `@a ` настраивается через `TRIGGER_PREFIX`.
Если провайдер ещё не настроен, бот сам подскажет команду для добавления.

## Провайдеры и агрегаторы нейросетей

Есть два равноценных способа задать провайдера — не обязательно выбирать
только один, можно использовать оба.

**Вариант 1 — из чата, без переменных окружения и без рестарта:**

```
!ai provider add openrouter openai_compatible https://openrouter.ai/api/v1 meta-llama/llama-3.3-70b-instruct:free sk-or-ВАШ_КЛЮЧ
```

Формат: `provider add <имя> <kind> <base_url> <модель> [api_key]`, где `kind` —
`openai_compatible` (OpenRouter, Groq, любой OpenAI-совместимый API) или
`gemini` (нативный Google AI Studio API). Провайдер сохраняется в SQLite
(там же, где история — переживает рестарт бота, если БД на постоянном
Volume). Эта команда доступна только владельцу аккаунта, на котором запущен
бот (даже пока `ADMIN_IDS` не задан — см. раздел "Права доступа" ниже), а
после отправки бот пытается сразу удалить сообщение с ключом из чата.

Переключиться на добавленного провайдера: `!ai provider openrouter`.
Удалить: `!ai provider remove openrouter`.

**Вариант 2 — заранее в `.env`, одной переменной `AI_PROVIDERS` в формате JSON:**

```env
AI_PROVIDERS={"openrouter":{"kind":"openai_compatible","base_url":"https://openrouter.ai/api/v1","api_key":"sk-or-...","default_model":"meta-llama/llama-3.3-70b-instruct:free"},"gemini":{"kind":"gemini","base_url":"https://generativelanguage.googleapis.com/v1beta","api_key":"AIza...","default_model":"gemini-2.0-flash"}}
```

- Ключ объекта (`openrouter`, `gemini`, ...) — это имя, под которым провайдер
  выбирается из чата.
- `AI_DEFAULT_PROVIDER` — какой провайдер использовать, если в чате свой не
  выбран. Если не задан и провайдер ровно один (из `.env` и/или из чата
  вместе) — используется он; если провайдеров несколько — нужно выбрать явно
  командой `!ai provider <имя>`.

Провайдер, добавленный из чата с тем же именем, что и в `AI_PROVIDERS`,
перекрывает его (считается более свежей настройкой).

Старый однопровайдерный формат (`AI_KIND` / `AI_BASE_URL` / `AI_API_KEY` /
`AI_MODEL`) по-прежнему работает как раньше.

## Команды из чата

Команды начинаются с `!ai` (настраивается через `COMMAND_PREFIX`):

| Команда | Что делает |
|---|---|
| `!ai id` | узнать свой ID (для `ADMIN_IDS` в `.env`) |
| `!ai help` | список команд |
| `!ai status` | текущие настройки этого чата |
| `!ai providers` | список доступных провайдеров/агрегаторов |
| `!ai provider <имя>` | сменить провайдера для этого чата |
| `!ai provider add <имя> <kind> <base_url> <модель> [api_key]` | добавить провайдера из чата |
| `!ai provider remove <имя>` | удалить провайдера, добавленного из чата |
| `!ai model <модель>` | сменить модель для этого чата |
| `!ai system <текст>` | задать системный промпт для этого чата |
| `!ai system clear` | сбросить системный промпт |
| `!ai search on` / `off` | вкл/выкл автодополнение ответов веб-поиском |
| `!ai engine searxng` / `keenable` | выбрать поисковый движок для этого чата |
| `!ai find <запрос>` | разовый веб-поиск (без обращения к нейросети) |
| `!ai history [n]` | последние n обменов (по умолчанию 5) |
| `!ai reset` | очистить сохранённую историю переписки с ИИ в этом чате |

### Права доступа

Команды делятся на три уровня:

- **Открыты всем**: `help`, `id`, `status`, `providers`, `find`, `history`.
- **Обычные настройки** (`provider <имя>`, `model`, `system`, `search`,
  `engine`, `reset`) — по умолчанию доступны любому, кто пишет боту (это
  личный userbot, чат по умолчанию считается доверенным). Если бот стоит в
  общих группах, задайте `ADMIN_IDS` в `.env` (ID через запятую, узнать свой —
  командой `!ai id`) — тогда эти команды будут работать только для
  перечисленных пользователей.
- **Чувствительные** (`sh`, `provider add`, `provider remove`) — требуют
  явного `ADMIN_IDS`, "пустой список = разрешено всем" здесь не действует.
  Единственное исключение: пока `ADMIN_IDS` вообще не задан, эти команды
  всё равно доступны владельцу аккаунта, на котором физически запущен бот
  (сравнивается с `client.me.contact.id` из PyMax) — иначе для первой
  настройки провайдера пришлось бы редеплоить бота ради одной переменной.
  Как только `ADMIN_IDS` задан — это правило перестаёт действовать, и
  список `ADMIN_IDS` становится единственным источником прав.

> ID отправителя берётся из `message.sender`. Если в вашей версии PyMax это
> не просто число, а объект — поправьте сравнение в `commands.is_admin` /
> `commands.is_strict_admin` (например, на `sender_id.id`).

## Веб-поиск (SearXNG / Keenable)

Два движка на выбор:

- **SearXNG** — свой self-hosted инстанс. Укажите `SEARXNG_URL` в `.env`
  (например, `http://localhost:8080`); используется его JSON API (`/search?format=json`,
  в самом SearXNG формат `json` нужно включить в настройках инстанса).
- **Keenable** — публичный поисковый API для AI-агентов (`https://keenable.ai`),
  работает без ключа (с более низким лимитом запросов); `KEENABLE_API_KEY`
  в `.env` — опционален, поднимает лимит.

Включить поиск можно двумя способами:
- на постоянку для чата: `!ai engine searxng` (или `keenable`), затем `!ai search on` —
  тогда каждый запрос к `@a` дополнительно ищет в интернете и добавляет
  найденное нейросети как контекст;
- разово, не трогая настройки чата: `!ai find <запрос>` — просто вернёт
  результаты поиска в чат.

Если поиск включён, но сходил с ошибкой (сеть недоступна, движок не настроен),
бот не падает — просто отвечает без веб-контекста.

## История и контекст диалога

Каждый вопрос и ответ сохраняются в `cache/history.db` (SQLite, путь —
`HISTORY_DB_PATH`). При следующем обращении к `@a` в этот же чат последние
`HISTORY_CONTEXT_TURNS` пар (по умолчанию 6) подмешиваются в запрос к нейросети,
так что бот "помнит" контекст беседы в рамках чата. `!ai reset` очищает историю
для текущего чата, `!ai history [n]` — показывает последние обмены.

## ⚠️ Выполнение команд в контейнере (`!ai sh`)

Есть возможность выполнить произвольную shell-команду внутри контейнера, где
работает бот, и получить вывод сообщением в чат. **По умолчанию выключено**
(`SHELL_EXEC_ENABLED=false`) — включайте только осознанно.

**Почему это опасно, а не просто "ещё одна команда":**
- Команда выполняется с теми же правами, что и сам процесс бота — то есть
  видит файловую систему контейнера, переменные окружения (включая ваши
  API-ключи из `AI_PROVIDERS`), сеть контейнера. Это не песочница.
- Кто угодно, кто получит возможность писать в чат от имени/в адрес этого
  бота с правами из `ADMIN_IDS`, получает управление сервером, а не только
  ботом.
- MAX (`pymax`) — неофициальный API, за его защиту от угона сессии/аккаунта
  Anthropic и Railway ответственности не несут — это ещё один повод не
  привязывать к аккаунту прямой доступ к серверу без крайней необходимости.
- Все выполненные команды и их вывод остаются и в логах Railway, и в истории
  переписки MAX — не выполняйте команды с секретами в аргументах.

**Как включить безопаснее:**
1. В `.env` задайте `SHELL_EXEC_ENABLED=true`.
2. Обязательно задайте `ADMIN_IDS=<ваш числовой ID>` (узнать его — командой
   `!ai id`) — **только ваш**, не
   оставляйте пустым и не добавляйте других людей. Для этой конкретной
   команды общее правило "`ADMIN_IDS` пуст = разрешено всем" **не работает**:
   пустой список означает полный запрет `!ai sh`, а не разрешение.
3. При необходимости уменьшите `SHELL_EXEC_TIMEOUT` (по умолчанию 30 секунд) —
   команда, которая не уложилась в таймаут, принудительно убивается.
4. Если сомневаетесь, нужна ли вам эта команда вообще — не включайте её;
   для диагностики контейнера обычно достаточно логов Railway (`railway logs`).

Вывод команды в сообщении обрезается до ~3500 символов, чтобы не упереться в
лимит длины сообщения MAX. Если полный вывод длиннее — бот присылает обрезанный
текст в сообщении **и отдельным файлом** (`output.txt`) полный, необрезанный
вывод, так что ничего не теряется.

## Структура проекта

```
main.py          — точка входа, обработчики on_start/on_message
config.py        — .env, провайдеры/агрегаторы, настройки поиска
storage.py       — SQLite: настройки по чатам + история вопросов/ответов
ai_providers.py  — обращение к нейросетям (openai_compatible / gemini)
websearch.py     — SearXNG / Keenable
commands.py      — обработка команд !ai ...
Dockerfile       — образ для деплоя (в т.ч. на Railway)
railway.json     — конфиг сервиса Railway (worker, без HTTP healthcheck)
```

## Проверка потребления памяти локально (без Docker)

Docker для этого не обязателен — тот же процесс, что будет крутиться на
Railway, можно замерить прямо в venv:

```bash
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt
python main.py &
PID=$!
sleep 20            # дождаться подключения к MAX
ps -o rss,vsz,cmd -p $PID   # RSS в килобайтах — реальная память процесса
kill $PID
```

Если хочется замерить именно в условиях, близких к контейнеру Railway:

```bash
docker build -t max-ai-bridge .
docker run --env-file .env -it --rm max-ai-bridge &
sleep 20
docker stats --no-stream
```

## Деплой на Railway

Бот — это постоянный воркер с сокет-соединением к MAX, а не HTTP-сервис,
поэтому важны несколько моментов, которых нет в типичных гайдах по Railway:

1. **Создайте сервис из репозитория** (или `railway up` из этой папки).
   Railway увидит `Dockerfile` и `railway.json` и соберёт образ сам — ничего
   дополнительно настраивать в build-команде не нужно.
2. **Не добавляйте HTTP healthcheck и не привязывайте публичный домен/порт**
   в настройках сервиса — бот не слушает порт, `railway.json` уже настроен
   без `healthcheckPath`, Railway будет просто следить за тем, что процесс жив.
3. **Подключите Volume** и примонтируйте его на `/app/cache`. Это критично:
   без Volume файловая система контейнера эфемерна, и при каждом передеплое
   вы потеряете:
   - `cache/main.db` — сессию MAX (без неё придётся заново вводить SMS-код
     при каждом деплое);
   - `cache/history.db` — сохранённую историю переписки с ИИ.

   В интерфейсе Railway: Service → Settings → Volumes → Add Volume → Mount
   path `/app/cache`.
4. **Задайте переменные окружения** во вкладке Variables — те же, что в
   `.env.example` (`MAX_PHONE`, `AI_PROVIDERS` и т.д.). Сам файл `.env` в
   образ не попадает (см. `.dockerignore`) — это осознанно, секреты не должны
   лежать в Git/образе.
5. **Первый вход по SMS-коду** — при первом старте PyMax запросит код в
   логах. Проще всего один раз авторизоваться локально (`python main.py`),
   дать сессии сохраниться в `cache/main.db`, и уже готовый файл сессии
   положить в подключённый Volume (через `railway volume` в CLI или
   веб-файловый менеджер Volume) — тогда на самом Railway код вводить не
   придётся.

Если план на Railway тарифицируется по факту потребления CPU/RAM (а не по
факту "простоя HTTP") — возвращаемся к тому, с чего начали: воркер с сокетом
не бывает "спящим" в терминах Railway, он всегда числится активным. Но за счёт
`python:3.12-slim` и минимума зависимостей (всего 3 пакета) базовое
потребление памяти должно быть небольшим — точные цифры даст тест выше.
